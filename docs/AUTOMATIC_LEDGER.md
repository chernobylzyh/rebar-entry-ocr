# 自动匹配与最终台账核验（2026-10-16）

> **2026-10-19 核验显示策略更新**：已唯一匹配、关键词一致且有来源证据的字段，成功关联说明只保存在 `match_notes`/`review_notes`，不再因为通用的边界或流程提示标红；实际读数冲突、尚未确认的关联及缺失/未识别字段继续提示人工核验。质证书与铭牌炉批号不一致、清单与证书编号不一致等冲突仍保留双方原文和定位。字段值、OCR、匹配约束、未识别逻辑和人工补正流程不变。以下将单纯边界说明一律标红的描述为历史规则，以本条为准。当前实现版本为 `matched-fields-conflicts-v1`，迁移与浏览器核验见 `experiments/analyses/analysis-20261019T080500Z-conflict-only-review.md`。

本说明描述当前自动匹配和最终字段核验流程。当前界面以 `前端/vue` 为准，Java 管理最终补正、确认和导出，Python 管理本地 OCR、自动关联与不可变的来源证据。

## 关联规则

|进场记录关键词|自动流程|失败处理|
|---|---|---|
|编号列存在且该行确有质量证明书编号值|先填清单编号；精确编号检索质证书 → 用证书炉批号检索独立铭牌 → 同页或牌号与规格关联送货单|清单缺牌号或规格不阻断证号/炉号链；可得关键词若明确矛盾则保留异常。编号不完全一致时标红并保留双方位置，不悄悄改走规格路径|
|缺少质量证明书编号|同一独立铭牌内同时匹配牌号与直径 → 关联送货物理行 → 用该铭牌炉批号检索质证书|缺少任一关键词、多个铭牌、多个质证书或多个送货行时保留候选，不任意选择|

自适应路径读取每一行的实际值：只有编号表头、编号格为空时，仍走规格与牌号路径。厂家、型号、规格分别成列时，各列只从同一物理行取值；自检结果等非目标列也参与划分边界，避免“合格”混入数量。

两条路径采用不同的主匹配键。有有效清单证号时，先按该证号找到质量证明书，再用证书炉批号定位独立铭牌；清单未填牌号不阻断此路线，也不回填或改写清单原记录。已知牌号、规格若与铭牌明确矛盾，或证书含多炉批且无法唯一定位铭牌，仍保留异常和候选。没有清单证号时，所选独立铭牌必须与清单同一行的牌号、规格（钢筋直径）同时完整且一致，之后才通过铭牌炉批号反查证书。

证书与铭牌炉批号同长度且仅一个英文字母不同时（如 `CE2603337` / `CB2603337`），系统只在证书和铭牌炉批号各唯一、差异恰为一个英文字母、铭牌炉批号字段本身唯一且无 OCR 警告时，按该唯一候选自动关联。台账炉批号写入铭牌识别到的原文（本例为 `CB2603337`），不改写任一侧 OCR 字符；字段同时标记待核验，并保留证书值、铭牌值、差异字符序号、双方证据位置和 `certificate_nameplate_heat_conflict` 原因，供人工检查。四表来源齐备且没有其他阻断问题时，行状态为 `matched_with_conflicts`，表示已自动关联但仍有矛盾待核验；这不等于字段已人工确认。证书或铭牌值不唯一、铭牌炉批号有警告、存在多个匹配铭牌时仍仅保留候选，不自动选择。数字或标点差异不触发这种单字母自动关联，也不会因一个泛化炉批号冲突而回填。清单牌号缺失时，候选检索仍要求已知规格一致、证号和炉批证据明确，且没有已知牌号/规格冲突或铭牌边界问题。未唯一确认的候选不填字段，也不计入已关联的四表来源；证据可分别跳转到证书页和铭牌页。

证号路线另有一项严格受限的全页铭牌例外：当清单编号精确命中唯一质量证明书、证书只有一个可靠炉批号，并且该炉批号精确命中唯一的全页解析铭牌；该铭牌在全页文本中只形成一个完整且结构一致的铭牌记录（公司标题、牌号、规格和炉批号均能归到该记录），没有第二个可能的铭牌，也没有已知字段冲突时，可以沿证书炉批号链自动关联。该例外只解决缺少铭牌 ROI 边界框的情况，不放宽任何匹配键，也不适用于没有清单证号的规格路线、含多个铭牌的整页读数或热号候选。台账保留铭牌字段原文，物理边界说明保留作来源注记；当表单已唯一关联且关键词无冲突时，该注记不单独标红。若全页存在多个结构化铭牌或无法将字段归到同一记录，仍列为候选并保留待确认状态。

送货单（含“发货单”）的关联先看页面布局：

1. 铭牌和送货单同页时优先关联该页送货单。该送货单页已和铭牌同页时，不再作为其他页同规格铭牌的跨页候选，避免重复占用。同一张送货单可承载多条货物行；多个同页铭牌可以共享该送货单的表头身份、顶部供应单位和编号，但每个铭牌必须按自身牌号与规格绑定对应的物理货物行。供应单位属于表单级字段，可以在多条台账行重复；重量、规格等货物行字段必须来自各自选中的行，不能把第一行重量或其他行规格复制给其他铭牌。若物理行无法唯一绑定，仍可保留已确认的同页表头和供应单位，但须明确标记货物行未确认，不能借用任一未选行的数量或规格。
2. 文件将铭牌和送货单分开编排时，直径/规格必须严格相同，牌号按其中唯一可辨认的强度数字比较。例如 `HRB500E`、`HBE500E`、`1级B500E` 可按 `500` 关联；OCR 将 `400` 误读为 `3400` 时，只有带有效牌号前缀的 `HRB3400E` 或 `1级B3400E` 才可按右端 `400` 形成待核验候选，并保留原文及“忽略前置数字3”的说明。裸 `3400`、缺少有效前缀的 `B3400E`、`400` 与 `500` 不同、数字缺失或互相冲突、规格不同均不能自动关联。原 OCR 字符不会被改写。
3. 无法按上述条件唯一匹配时，保存异常原因及最接近候选的原文、差异和位置，供最终核验。多个送货单满足相同数字牌号及规格时保留多候选；不能任意选一个。牌号数字放宽仅用于铭牌与送货单，清单与铭牌、证书编号及炉批号匹配仍按各自原规则。

全页与局部 ROI 若来自同一页、顶部供应单位一致，且两种编号只在首字母上不同、其余长数字/字母后缀完全相同（例如 `XSD202603270667` 与 `KSD202603270667`），可作为同一张物理送货单的两个 OCR 视图合并表单身份。表单关联和共同识别到的供应单位可以保留，货物行仍须按规格/牌号独立确认；两个编号不得自动择一或改写，送货单编号字段留空并标红，列出两种 OCR 原文及各自全页/ROI 证据位置。若供应单位不同、编号后缀也不同、页上确有多个物理送货单，或视图无法证明来自同一表单，则不能合并为一个已确认表单，须分别列出候选。局部 ROI 被截断或重复时，应在诊断中指出该视图的质量问题；不得因它没有读出货物行而丢弃另一完整视图的行证据。

不同铭牌即使炉批号相同也保留独立 ID。同一铭牌或送货物理行被多条进场记录命中时提示重复或资源冲突，不合计数量。同页不同铭牌共用同一送货表头本身不属于重复资源；若各自匹配到不同货物行，应保留不同的行 ID，共用供应单位。只有多条记录实际争用同一物理货物行时，才提示重复/资源冲突。

进场清单跨页/跨表单出现相同的非空质保书编号时，自动台账按PDF页码、清单行号顺序只保留首次记录。其余行的来源 ID、页码、证据、OCR问题和字段差异合并到首条记录，证号字段显示合并诊断并可跳转到各来源位置；重复验收数量不会相加，后续行字段不会覆盖首条。牌号/规格/数量等非空值若互相矛盾，诊断会列出冲突及候选值，首条值保留待人工核验。质保编号为空或占位符的记录不参与此去重。原始OCR文件和原始提取记录不被改写；去重发生在匹配和最终台账生成入口。

每条去重后的进场记录都生成最终可编辑行；匹配不足不会中断或要求人工捆绑。没有可靠证据的字段留空。存在多个不同 OCR 值时保留全部候选、原文和位置。

## 最终字段来源

|字段|取值来源|不确定时定位|
|---|---|---|
|供应单位|对应送货单/发货单顶部的公司名称|该送货单所在页、公司标题区域；不从购货单位或铭牌生产厂家补值|
|送货单编号|对应送货单右上方 `No.` / `NO:` 后的字母与数字，保留前导零|该送货单所在页及编号标签区域；多张单同页时分别定位|
|生产单位|所选独立铭牌最上方的公司名称|该铭牌所在页和独立卡片区域；不借用其他铭牌或送货单标题|
|验收数量|进场数量清单/进场检验记录同一行的进场数量，按明确单位规范化|该进场行数量格；缺失时保留异常，不用送货重量替代|
|质保书编号|优先保留进场清单同一行已提取的编号；若唯一质量证明书页读到完全相同且无冲突的编号，字段仍保留清单值但主定位更新为该证书页；清单格无值时才直接采用证书编号|证书唯一精确确认时主定位证书页并保留清单原格证据；编号不完全一致、未找到对应证书或不唯一时主定位清单编号格，保留双方页码和位置并标红|

送货行重量可以作为对照证据，和进场数量不同时保留差异；它不覆盖验收数量，也不补填缺失的进场数量。编号、供应单位或生产单位未读取到时仍应跳到对应来源页，不能默认跳回进场表。

清单质保书编号已填入并不表示证书已完全匹配。唯一精确证书确认时，台账显示的编号仍是清单原值，但字段页码更新为证书页，同时保留清单格位置；后续炉批号、铭牌或送货单链路失败不会撤销这个证号定位。红色字段继续保留原值、冲突原因和对照证据，等待最终导出前集中核验；不会用证书候选覆盖清单原值。

## 多铭牌登记

先利用牌号锚点、公司标题与列间空白确定独立区域，轮廓检测作为补充，再对每个区域单独运行 OCR。区域边界、裁剪图片、独立实体 ID 和原图多边形全部保存。全页 OCR 保留作证据，但已经拆出的铭牌不再使用全页字段池进行匹配；独立区域内缺少生产单位时也不借用旁边铭牌的公司名称。

规格和牌号必须从同一实体读取；炉批号或规格不唯一时保留异常。任意粘贴、遮挡或重叠版式可能使区域边界不明确；此时应在最终核验看到缺失或歧义，不能通过跨卡拼字段提高表面覆盖率。

## 诊断与位置

`automatic_ledger.records` 含 `fields`、`match_route`、`match_path`、`matched_heat_lots`、`match_status`、`diagnostics`、`match_candidates` 和 `sources`。`match_path` 显示本行采用的四表顺序。`matched_heat_lots` 始终表示已选铭牌与已选证书的**精确炉批号交集**，不进行模糊归一；所以单字母差异虽可唯一自动关联并将铭牌原文写入 `fields.炉批号`，`matched_heat_lots` 仍为空。此时 `sources.nameplate` 的 `association_method` 为 `unique_single_letter_heat_difference`，并带双方原值；炉批号字段及整行诊断含 `certificate_nameplate_heat_conflict`、`association_status=auto_matched_with_heat_conflict`、`written_heat_lot` 和双方 `locations`。该唯一关联候选的 `match_candidates` 项标记 `review_only=false`、`write_allowed=true`，其中 `write_allowed` 指允许采用已识别的铭牌原文作为台账值，不表示可覆盖或修正证书 OCR 原文。物理边界或视图差异等成功关联说明保存在 `match_notes`/`review_notes`；只要表单与关键词均已确认且字段自身无冲突，就不单独标红。实际证号/炉批号/读数冲突、未唯一确认的关联和缺失字段仍保留红色或未识别提示。未唯一确认的冲突候选保持 `association_status=candidate_only`、`review_only=true`、`write_allowed=false`，不填台账炉批号，也不计为自动关联。指标 `automatic_complete_rows` 只计无矛盾的 `matched` 行，`automatic_matched_with_conflicts_rows` 单独统计已关联但待核验的行。典型诊断还包括 `missing_keyword`、`unclear_ocr`、`conflicting_values`、`duplicate_resource`、`multiple_match_candidates`、`specification_mismatch_candidates`。

诊断必须指出失败发生在哪一步，避免只写“未唯一确认”。例如应区分“清单证号未命中证书”“已找到证书但证书炉批号未识别”“证书炉批号未命中铭牌”“全页唯一结构化铭牌热号精确命中，但缺少铭牌 ROI 边界框，需核对第 N 页”“铭牌已确认，但未找到规格和牌号均符合的送货货物行”“送货表头已由同页位置确认、供应单位一致，但全页与 ROI 的送货单号首字母冲突（列出两值），编号待核验”“同页有多个物理送货表单无法区分”。每条诊断应附失败步骤的来源页及可用 ROI/字段证据；确定表单但字段冲突时保留可确认字段（如供应单位），只将冲突字段（如送货单编号）留空标红。

位置包含 `page_no`（从 1 开始）、`polygon_page`（原 PDF 渲染图左上角像素轴）、`source_pixel_size` 和必要的 `render_dpi`。首页固定模板使用 300 DPI，附件通常 180 DPI；接口按实际显示尺寸和用户旋转换算坐标。没有可靠文字框时退回来源页定位，不虚构关键词坐标。原始 PDF 和裁剪图均保存在运行目录。

页面 OCR 的台账框提供明确 `records[i].字段` 路径。同页同值不会通过文字模糊匹配定位到另一个铭牌。诊断和候选按钮按各自证据定位。

## 当前接口

Python（8000）返回原始 JSON，Java（8080）包装为 `{code,data,msg}`，Vue 请求 Java：

- `POST /api/pdf/to_images`：PDF 渲染；支持当前前端发送的 PNG/png。
- `POST /api/library/upload`、`GET /api/library`：库管理。
- `POST /api/library/{name}/recognition`：异步提交整卷任务，Python返回202及任务状态；同卷重复提交返回同一排队/运行任务，不重复启动OCR。
- `GET /api/library/{name}/recognition`：查询排队位置、实际管线阶段及该阶段`current/total`；Java完成本地台账和页面OCR同步后返回`local_ready:true`。模型加载等无可测页数的阶段显示不定进度。
- `GET /api/library/{name}/ledger`：读取自动台账；旧`POST .../recognize`作为阻塞兼容接口，复用同一任务。
- `GET|POST /api/library/{name}/pages/{page}/ocr`、`GET .../image`：图像和带路径的证据框。
- `POST .../pages/{page}/rotate`：Python 使用逆时针角度，Java 将本地顺时针角度转换后传入。只旋转源页显示并刷新本页证据框，保留整卷台账、人工补正、版本和已完成核验；坐标读取失败时隐藏失效框，台账仍可查看。
- `POST /api/library/{name}/resplit`、`POST .../cache`：同步清理提取或台账缓存。已有OCR缓存只需清理台账再启动识别，即可从保存OCR重新解析清单并匹配；`force_ocr_refresh=true`才重新运行OCR。
- Java `PATCH /api/library/{name}/ledger/field`：最终补正，保留原值、证据和诊断，使原核验失效。Java CORS 已允许 `PATCH`，前端兼容 JSON 与文本错误响应，避免将 `Invalid CORS request` 误解析成 JSON。
- Java `POST .../ledger/review`：校验版本和关键必填字段后确认最终核验；`GET .../export`：未确认禁止导出。总台账导出同样检查各卷确认状态。

Java 当前单次上传限制为 50 MB；Python 层上限为 256 MB。前端部署应使用 Java 入口。

不同卷进入本地OCR队列顺序执行；一卷识别时可以上传和提交其他卷。当前卷仍在排队或识别时，不能修改其源文件、缓存或页面。完整任务恢复、重复提交与进度约定见 [OCR任务与进度接口](RECOGNITION_JOBS.md)。

## 更新后复用已有OCR

重启Python与Java服务，并重新构建或启动当前`前端/vue`后，打开已有卷，选择「清除台账」，再点击「识别整卷 PDF」。此时只从保存的OCR重新解析进场数量、构建物理表单和自动匹配，不下载模型或重新执行OCR。「清除全部缓存」会在下一次识别重新运行OCR，请按需要选择。重算后的台账需要重新进行导出前核验。

人工保存与旋转修复在更新 Java 和 Vue 后即可用于已有台账；不需要清缓存。清单编号优先、编号冲突标红以及证号/规格两条匹配路线需要按上述方式重新生成旧台账，刷新页面不会自动改写旧结果。

已有人工补正需要保留时，先导出或保留当前结果副本；清除台账会清除该卷的台账和核验状态。缓存回放验证使用独立实验目录，未替换服务库中已有的人工结果。

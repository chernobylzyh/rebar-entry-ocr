# 网页启动、核验与导出

当前入口为 Vue 工作台，流程是上传 PDF、自动提取与匹配、集中核验最终台账字段、导出。当前工作台最终模型为本地 GLM-OCR（`local-glm`），匹配与台账规则沿用既有实现。匹配过程中不要求人工捆绑候选。最新模型环境和三服务命令见 [GLM-OCR 使用说明](GLM_OCR.md)，规则与接口见 [自动台账说明](AUTOMATIC_LEDGER.md)。

## 启动与上传

Python OCR 服务使用 8000，Java 业务服务使用 8080，Vue 开发服务通常使用 5173。启动后打开 Vue 终端显示的地址；开发代理将 `/api` 和 `/image` 转发给 Java。

在「上传识别」页面选择 PDF，上传后在历史记录中打开，或在结果页选择该卷。Java 单次上传限制为 50 MB。新安装没有开发者的历史文件，空列表是正常状态。

同名且内容、DPI 相同的覆盖上传会复用原卷、页面和人工核验；内容改变时才会归档旧卷并建立新卷。上传与渲染成功仅表示文件可查看，还需执行整卷识别生成台账。

## 自动识别与原图核对

点击「识别整卷 PDF」。系统使用本地 GLM-OCR 和自动匹配规则，缺失、冲突、重复和多个候选会保留诊断，全部进入最终核验。已有四卷可直接打开识别，无须重复上传；保持「强制重跑 OCR」未选中，先复用可校验的 GLM JSON 缓存，只补识别缺失页。

一卷识别期间可以继续上传和提交其他卷，任务将顺序执行；同卷重复提交复用现有任务。页面显示排队位置或实际阶段页数，刷新及切换卷后会恢复任务状态。加载模型和自动匹配没有可测页数时显示不定进度，不使用固定耗时估计。

单击台账单元格或诊断中的页码，查看对应原图和位置框；双击单元格补正。没有可靠坐标时只能定位来源页，应结合原图核对。候选用于查看证据，不能把相邻页面或同炉号直接当成对应关系。

铭牌在两条匹配路径中都必须与进场清单同一行的牌号和规格（钢筋直径）同时完全一致。只有牌号相同、只有炉批号相同或缺少其中一个关键词时，保留候选及原因，供最终核验。

质保书编号优先显示进场清单已提取的值。若唯一质量证明书页读到完全相同且没有冲突的编号，表格仍显示清单值，但该字段主页码更新为证书页，并保留清单编号格作为对照证据；点击字段可先定位证书，诊断或证据位置可回到清单。编号不完全一致、未找到唯一证书或对应证书页不唯一时，保留清单页主定位并标红；后续炉批号、铭牌或送货单关联失败不会撤销已精确确认的证号定位。清单编号格为空时才使用关联证书编号。

使用源页区的「旋转90°」调整原图方向时，右侧台账、人工补正和已完成核验保持不变，证据框随当前页重新加载。旋转后的框暂时加载失败不会清除台账。

## 核验与导出

核对材料名称、规格、生产单位、供应单位、送货单编号、日期、使用部位、炉批号、验收数量和质保书编号等关键字段，并处理缺失、冲突和重复提示。没有可靠依据的值保持待核验，不猜测填入。

完成补正后点击「核验关键字段」。缺少必填字段或台账版本已变化时无法确认。确认后可导出 Excel；导出包含「台账」和「字段溯源」。修改字段或重新识别会使旧核验失效，需要再次确认。

双击补正后保存会通过 `PATCH` 更新台账；刷新台账或重新打开该卷可查看保存值。原始 OCR 和诊断继续保留，人工保存不会把冲突字段伪装为 OCR 已确认。

字段异常与候选在固定区域内滚动查看，首次点击不会把下方表格推移，双击可直接打开补正框。

## 缓存与排错

|现象或操作|处理方式|
|---|---|
|页面能打开，上传或历史记录报错|检查 Java 8080 是否启动，以及 Vite 代理目标|
|上传或识别请求失败|检查 Python 8000、Java 的 `OCR_BASE_URL` 和双方日志|
|首次 GLM 识别或加载失败|检查 `.venv-glm/bin/python`、离线共享的 `models/GLM-OCR/` 和 GPU 配置；自定义位置使用 `MATERIAL_OCR_GLM_PYTHON`、`MATERIAL_OCR_GLM_MODEL_DIR`。不要重复下载到运行目录|
|字段缺失或多个候选|查看诊断、原文和来源页，在最终台账中核对补正|
|补正报 `Invalid CORS request` 或 JSON 解析错误|更新并重启 Java，重新构建或刷新当前 Vue；CORS 已支持保存所需的 `PATCH`，文本错误也会显示原始原因。无需清除现有台账|
|旋转后右侧台账消失|更新 Java 与 Vue 后再旋转；新行为保留台账和核验，只刷新源页。旧版本已删除的台账需要从备份恢复或用 OCR 缓存重新生成|
|规则改动后复用旧台账|重启相关服务，清除台账缓存后重新生成|
|只清台账|保留OCR缓存，再点「识别整卷 PDF」即可重读进场清单并重新匹配，无需重跑OCR；台账补正与旧核验会失效|
|清全部缓存或重新切分|使提取或台账缓存失效，按页面提示重新识别|
|导出按钮不可用或接口拒绝|先完成当前版本的关键字段核验|

应用清单编号优先、冲突标红和铭牌双关键词规则时，先保留已有人工结果副本，再更新 Python、Java 和 Vue，打开该卷「清台账」后点击「识别整卷 PDF」。保持「强制重跑 OCR」未选中，即可使用本地缓存重算；重新生成会清除旧台账补正及核验，需再次核验。只使用人工保存或旋转修复时，更新 Java 和 Vue 后即可生效，不必重算。

Python 的上传与提取结果位于 `runs/web/library/`，Java 的文件默认位于 `前端/image/library/`，本地数据库位于 `前端/runtime/h2/`。这些目录及日志、导出文件不属于交付内容。接收方检查步骤见 [核验说明](ACCEPTANCE.md)。

## 空间占用

当前工作台的 GLM 推理由 `.venv-glm` 子进程运行，直接共享离线 `models/GLM-OCR/`，不复制权重。整页和 ROI 在内存中处理，保存逐页 JSON checkpoint，不为每次重算复制 PDF、页面或裁区 PNG。普通重复提交复用任务与有效缓存；真实重新推理和仅缓存匹配会分别记录，不能把缓存验证称为新 OCR 实测。

历史 Paddle 流程仍默认使用 `compact` 保存策略；成功任务只移除已验证可原样重建的诊断 PNG，保留 PDF、完整页面、OCR 文本和坐标、台账与人工核验所需的数据。失败和中断任务保留现场，便于排查。

需要完整诊断图片时，在 Python 启动或 `analyze` 命令中添加 `--artifact-policy full`，也可设置 `OCR_ARTIFACT_POLICY=full`。默认无需设置环境变量。已移除的诊断图可用 `python -m material_ocr.storage_artifacts --restore <图片路径.png>` 恢复；其旁边的 `.artifact.json` 配方及源 PDF/整页图必须保留。现有旧缓存没有配方时不会被自动删除。

浏览器验证工具现在只准备选中的有效缓存与独立可写页面，运行结束后保留台账、数据库、PDF、命令、日志、截图和 trace，再回收其自身产生的可重建图片与 Vite 缓存。使用 `--keep-stack-data` 可保留本次全部调试文件。

“清台账”或“清全部缓存”表示使结果失效，不等于释放旧目录空间。不要手工清空 `runs/` 或 `experiments/`；先按 [存储维护说明](storage_maintenance.md) 生成引用保护清单，再处理可确认的重复数据。
